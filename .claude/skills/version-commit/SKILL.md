# Версия и сообщение коммита

Задача: по текущим изменениям в рабочем дереве определить, как поднять версию, записать её и подготовить сообщение коммита.
**Не выполняй** `git add`, `git commit`, `git tag`, `git push` и ничего, что меняет историю или индекс. Это делает пользователь.

Аргументы пользователя: `$ARGUMENTS`. Если там явно указан `major`, `minor`, `patch` или `none`, это решение пользователя: используй его вместо своей оценки (но скажи, если не согласен). Остальной текст — подсказка о смысле изменений.

## Как устроена версия

- Единственный источник — `version.properties` в корне: строка `version=MAJOR.MINOR.PATCH`.
- `app/build.gradle.kts` читает её: `versionName = MAJOR.MINOR.PATCH` (у debug-сборки суффикс `-debug`), `versionCode = MAJOR*10000 + MINOR*100 + PATCH`. Поэтому MINOR и PATCH должны быть < 100. Если подъём упирается в 100, предложи пользователю поднять разряд выше и не меняй файл без его ответа.
- `versionCode` должен только расти, иначе Android не обновит приложение поверх старого. Никогда не уменьшай версию.
- История — `CHANGELOG.md` (на русском, формат Keep a Changelog). Теги — `vMAJOR.MINOR.PATCH`.

## Шаги

1. **Собери изменения.**
   - `git status --short`, `git diff HEAD --stat`, `git diff HEAD` (staged и unstaged вместе). Неотслеживаемые файлы из `git status` прочитай отдельно, если они важны.
   - `git log --oneline -10` для контекста.
   - Если изменений нет, скажи об этом и остановись.
2. **Проверь, не поднята ли версия уже.** Сравни `version.properties` с `git show HEAD:version.properties`. Если в рабочем дереве версия уже отличается от HEAD (скилл запускали раньше для этого же коммита), не поднимай её второй раз: пересчитай подъём **от версии в HEAD** и при необходимости исправь файл и последнюю запись в `CHANGELOG.md`.
3. **Классифицируй изменения** по типам Conventional Commits:
   - `feat` — новая возможность, видимая пользователю (экран, функция, формат, настройка);
   - `fix` — исправление ошибки;
   - `perf` — производительность, расход памяти/диска, скорость буферизации;
   - `refactor`, `style`, `test`, `docs`, `build`, `ci`, `chore` — без изменения поведения для пользователя.

   Изменения в `roadmap.md`, `CLAUDE.md`, тестах, `tools/` и конфигурации IDE сами по себе на версию не влияют.
4. **Выбери подъём** (берётся самый сильный из всех изменений):
   - **major** — несовместимое изменение (см. ниже). Пока версия `0.x`, несовместимость поднимает **minor**, а переход на `1.0.0` — только по решению пользователя.
   - **minor** — есть хотя бы один `feat`. PATCH сбрасывается в 0.
   - **patch** — есть `fix` или `perf`, либо пользователь заметит изменение поведения/интерфейса (тексты, вёрстка, обновление зависимостей, влияющее на воспроизведение).
   - **none** — только `refactor/test/docs/build/chore` без видимого эффекта. Версию не трогай, в журнал не пиши.

   Несовместимым в этом проекте считается:
   - изменение протокола «Смотреть на ТВ» (`remote/RemoteProtocol.kt`, `LocalStreamServer`/`StreamDataSource`, NSD-атрибуты), после которого старая версия на телефоне или ТВ перестаёт работать с новой;
   - потеря пользовательских данных: Room-миграция с удалением данных, смена формата `LocalLibrary`/`UiPreferences`/токенов сопряжения без переноса старых значений;
   - смена `applicationId` или подписи.

   Если не уверен между двумя вариантами, выбери более сильный и объясни почему.
5. **Запиши версию**: поправь строку `version=` в `version.properties` (комментарии в файле не трогай).
6. **Допиши `CHANGELOG.md`**: новый раздел сразу под вводным абзацем, над предыдущей версией:

   ```
   ## [X.Y.Z] — ГГГГ-ММ-ДД

   ### Добавлено
   - ...
   ### Изменено
   - ...
   ### Исправлено
   - ...
   ```

   Только непустые подразделы. Пиши по-русски, с точки зрения пользователя («Субтитры больше не пропадают после перемотки»), а не названиями классов. Дата — сегодняшняя.
7. **Подготовь сообщение коммита** (на английском, Conventional Commits):

   ```
   <type>(<scope>): <summary в повелительном наклонении, до ~70 символов, без точки>

   <тело: что и зачем изменилось, по пунктам, если изменений несколько; строки до 72 символов>

   BREAKING CHANGE: <только при несовместимом изменении>
   ```

   - `type` — самый значимый тип из шага 3; `scope` — область: `torrent`, `player`, `remote`, `files`, `home`, `theme`, `ui`, `build`, `docs` (можно опустить, если затронуто многое).
   - Если версия поднята, последняя строка тела — `Version: X.Y.Z`.
   - Не добавляй строк вида `Co-Authored-By` и упоминаний Claude: коммит делает пользователь от своего имени.
8. **Ответь пользователю** коротко:
   - старая → новая версия и `versionCode` (или «версия не меняется» и почему);
   - какие файлы изменены скиллом;
   - сообщение коммита в блоке кода, готовое к копированию;
   - команды, которые пользователь выполнит сам (не выполняй их):

     ```
     git add -A
     git commit -F <файл с сообщением>   # или через IDE
     git tag vX.Y.Z                      # только если версия поднята
     git push && git push --tags
     ```

   Если в рабочем дереве есть явно посторонние файлы (логи, APK, локальные настройки), предупреди, что `git add -A` их захватит, и предложи перечислить файлы явно.
